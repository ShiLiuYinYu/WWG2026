# 架构重构设计：阶段场景差分与章节模块

> 状态：**S0–S4 已按阶段保留独立场景文件，基础 Prefab 差分与常驻运行时尚未实施**。已新增 `GameState`、`GameStateStore`、`StoryIds`；S0/S1 仍由原阶段控制器承担。S2–S4 现由独立章节控制器、地点场景与编辑器样本实现 P2、P3 和两种 24H 结尾，尚未迁入本方案规划的 `GameRuntime`/`ChapterModule` 常驻架构；本文后续相关条目仍是重构目标。
> 关联文档：[架构规范](./架构规范.md)、[目录结构组织](./目录结构组织.md)、[运行流程](./运行流程.md)、[程序规范文档](./程序规范文档.md)、[YarnSpinner 接入与对话系统重构](./YarnSpinner接入与对话系统重构.md)。

## 1. 现状问题

当前实现把「游戏阶段」同时编码进了**场景名、目录、控制器类**三处：

```text
Scenes/S0.unity, Scenes/S0/S0_Corridor.unity, Scenes/S1.unity, Scenes/S1/...
Scripts/S0/S0Controller.cs + S0Hotspot.cs
Scripts/S1/S1Controller.cs + S1Hotspot.cs
```

由此产生的问题：

1. **重复实现**：`S0Controller` 与 `S1Controller` 各自保留 HUD、面板开关、模态判断、检查点和字体注入；对白队列已由共享 Yarn 服务替换。
2. **重复场景缺少共同基准**：同一间活动室在 S0（白天）与 S1（夜间）是两个场景、两套控制器和两套热点，公共门窗/透视难以同步；但独立场景便于逐阶段调整物件，应保留。
3. **跨场景状态靠静态字段**：`pendingTravel`、`pendingArrival`、`WWG_S0_ManualCheckpoint`、`WWG_S1_Checkpoint` 分散，读档只覆盖单章，无法承载 S2–S4、P2/P3 和两次路线选择。
4. **共享 UI 依赖具体阶段**：`GameplayOverlay` 里到处 `if (s0 != null) ... else if (s1 != null)`，新增阶段必须改 UI。
5. **新增阶段成本高**：S2–S4 已各自创建场景族与控制器，状态和 UI 尚未统一；每加一章仍需重复实现公共流程。
6. **并行开发受阻**：若先合并全部 S0/S1 场景与控制器，再接入 S2，S2 会等待迁移完成；若所有章节组件写入同一个 `Gameplay.unity`，多程序员又会集中修改同一 Unity YAML 文件。

## 2. 设计原则

1. **阶段是运行时状态，也是场景选择条件。** `GameState.chapterId` 决定当前章节模块，并与 `locationId` 一起确定独立的阶段地点场景；同一阶段内的照明变化由 `locationVariant` 表示。
2. **场景按阶段和固定视角切分。** 同一地点在不同阶段保留独立 `.unity`，阶段专属物件与热点直接在所属场景中编辑；共用的稳定画面结构通过基础 Prefab 复用。
3. **一个状态源、一套服务。** 存档、对话、信息、备忘、暂停、物品栏只实现一次，所有阶段共用。
4. **章节逻辑模块化，但不隔离状态。** 每章一个 `ChapterModule` 组件，负责该章的交互与推进；共享服务与 `GameState` 由核心持有。
5. **阶段场景保留场景对象的编辑权。** 基础 Prefab 只承载跨阶段确实一致的静态空间结构；阶段专属图片、热点、交互层、照明和可调整位置留在阶段场景。常驻核心负责全局相机、EventSystem、共享 UI 和存档。
6. **代码按职责分目录。** `Core / Interaction / Dialogue / UI / Chapters / Data`；阶段场景目录与章节逻辑模块分别维护。
7. **可渐进迁移。** 旧 S0/S1 流程在新流程验收前保留；新旧入口通过明确开关隔离。每个集成节点至少有一条可玩的入口，最终再删除旧实现。
8. **S2 不以 S1 迁移完毕为前提。** 核心契约、S2 开发入口和前置状态样本先落地；S1 只需最终提供约定的交接状态。
9. **共享文件有负责人。** 章节代码、地点场景和其 `.meta` 可分支开发；核心接口、共享 UI、Build Settings 与常驻场景由集成人维护。

## 3. 目标结构

### 3.1 场景

```text
Assets/Scenes/
├─ Title.unity                 # Build 0，主菜单（保持现状）
├─ Gameplay.unity              # 目标常驻核心：相机/EventSystem/共享 UI/StoryDirector
├─ S0.unity                    # 已有 S0 楼外
├─ S0/                         # 已有 S0_Corridor / S0_ClubRoom / S0_Bridge
├─ S1.unity                    # 已有 S1 活动室
├─ S1/                         # 已有 S1_Corridor / S1_BridgeEntrance
├─ S2.unity                    # 已有 S2 单数栋 4F 入口
├─ S2/                         # 已有 S2 连廊中段、偶数栋入口与安全屋
├─ S3.unity                    # 已有 S3 机房
└─ S4.unity                    # 已有 S4 终章活动室

Assets/Prefabs/Locations/      # 目标基础 Prefab；逐个提取稳定公共画面，不批量重建
├─ ClubRoomBase.prefab         # S0/S1/S2/S4 活动室可共用的静态结构
├─ Corridor5FBase.prefab       # S0/S1 走廊可共用的静态结构
└─ BridgeOdd4FBase.prefab      # S0/S1/S2 入口可共用的静态结构
```

- `Gameplay.unity` 是目标常驻核心场景，由 `Title` 单加载；具体章节模块以各自预制体加载，避免每增加一章都修改 `Gameplay.unity`。现有正式入口仍直接加载 S0，不能把目标写成已实现。
- 每个阶段地点继续保留独立 Scene 和原 GUID。目标运行时按 `(chapterId, locationId)` 显式查表选取场景路径，再**叠加加载**（additive）；切换时先加载并校验新场景，再卸载旧场景。`locationVariant` 只表示同一阶段场景内的照明或短时演出状态，不选择另一阶段的场景。
- 场景承载基础 Prefab 实例、阶段专属画面与热点。基础 Prefab 只放经人工核对确实一致的静态结构、共同坐标基准；不能把 S0/S1/S2/S4 的不同光照底图、可动椅子、照片、资料柜、纪念盒或阶段热点强制合进同一个根节点。共用 UI 另由现有 `GameplayOverlay` 等预制体维护。
- 阶段场景的 Prefab override 可调整本阶段位置、显隐与样式；需要独立增删或重新绑定交互的对象直接留在场景。修改基础 Prefab 前检查所有使用它的阶段场景；不将某个阶段的 override Apply 回基础资产。抽取时在 Unity 编辑器逐场景核对引用和布局，禁止用文本替换 YAML 或脚本重建已人工调整对象。
- 目标常驻核心接管 Camera、EventSystem、AudioListener、共享 Overlay、控制器和存档后，阶段场景只保留地点画面/热点及其专用 Canvas；迁移前已有对象继续按当前流程运行。

> 这里的「阶段地点场景」指每个阶段的每个固定视角可点击画面。S0 白天入口、S1 夜间入口和 S2 调查入口可以共用基础 Prefab，但仍是三个可独立编辑的场景；4F 的单数栋入口、连廊中段和偶数栋入口也分别是场景。

- `StoryDirector` 以 `Resources/Chapters/<chapterId>` 的固定路径加载章预制体，并把实例挂到运行时 `Story Root`。仓库中的章节预制体彼此独立，不在 `Gameplay.unity` 中序列化。加载前校验资源与 `ChapterId` 是否匹配；缺失时显示可诊断的错误，绝不回退到另一章。
- `GameState.chapterId` 决定当前激活的模块及阶段场景。固定章节 ID 为 `Prologue`、`NightPhoto`、`BridgeRoute`、`ServerRecovery`、`Finale`；新增章节遵守同一命名契约。逻辑地点 ID 保持 `ClubRoom` 等稳定名字，场景路径另由章节和地点共同决定。
- 原 `S0Controller/S1Controller` 的共享能力上移到 `GameRuntime + DialogueService + InfoService + GameStateStore`；只把**该章独有的交互与推进**留在章节模块。
- `Core`、`Interaction`、`Dialogue`、`UI` 不引用具体章节类。章节只依赖公共接口和状态 ID；合并前用编译与最小 Play 路径验证此方向。

## 4. 核心对象契约

### 4.1 GameFlow

```csharp
public static class GameFlow
{
    public const string TitleScene = "Title";
    public const string GameplayScene = "Gameplay";

    public static bool StartNewGame();                // 清空/新建状态 -> Gameplay
    public static bool ContinueGame();                // 读取存档 -> Gameplay

```

- 只认识 `Title`/`Gameplay` 与 `(chapterId, locationId) → 场景路径` 映射；不在运行时根据名字拼路径或猜测回退场景。
- 场景映射集中在 `StoryIds.LocationScene(chapterId, locationId)` 或等价的显式注册表，覆盖现有 S0–S4 场景路径。未登记组合返回错误，不回退到同地点的其他阶段。旧 `S0Location/S1Location` 在原流程退役前保留。

### 4.2 GameState

```csharp
[Serializable]
public sealed class GameState
{
    public int version = 1;
    public string chapterId;        // 稳定章节 ID，与预制体路径一致
    public string stepId;           // 章内步骤 ID；仅由所属章节解释
    public string locationId;       // 当前地点
    public string locationVariant;  // "day" / "night" / ...
    public int san = 100;
    public int sanMax = 100;
    public int health = 3;
    public string timeId;           // 剧情时间段，不由场景名推导
    public List<string> flags = new();
    public List<string> inventory = new();
    public List<string> seenDialogue = new();
    public string routeChoice;      // RouteLight / RouteDark
    public string viewChoice;       // ViewTogether / ViewAlone

    public bool HasFlag(string id);
    public void SetFlag(string id);
    public bool HasItem(string id);
    public void AddItem(string id);
}
```

- 旧布尔字段统一为具名 flag，例如 `flag.s0.board`、`flag.p1.curtain`、`flag.p2.oddFarRead`、`flag.p2.evenFarRead`、`flag.p2.cabinetOpen`、`flag.p2.emergencyLightOn`。路线选择与灯的**当前开关状态**分开：选择 `RouteDark` 后允许再开灯，`routeChoice` 不被改写。
- 关键物品（旧照片、工牌）使用 inventory 字符串 ID，不再各控制器持有布尔。
- P2 借用便签、分工表残页和 P3 U 盘同样是不可丢弃的任务物；P3 后 SAN 上限提升用 `sanMax=120` 保存。对话触发记录用于读档去重；状态恢复不得重播已处理的一次性剧情冲击。
- ID 一经写入存档便保持稳定；新增 flag 不要求同时修改其他章节的文件。反序列化要补默认值并校验章节、地点、范围与互斥选择。

### 4.3 GameStateStore

- `WWG_Save` 是**最近一次有效检查点**，含 `version`；运行中的 `GameState` 是内存状态。手动存档与明确的剧情自动检查点才调用 `SaveCheckpoint(GameState)`，普通点击和地点切换不覆盖检查点。读档从检查点恢复一份新状态。
- 提供 `SaveCheckpoint(GameState)`、`LoadCheckpoint()`、`HasCheckpoint()`、`DeleteCheckpoint()`，以及读档错误结果。转场中、模态未结算或章节/地点不一致时禁止写入；先完整校验，再持久化。
- 旧 `WWG_S0_ManualCheckpoint` / `WWG_S1_Checkpoint` 提供一次性迁移：仅当新键不存在时尝试；转换后逐字段验证并成功写入新键才标记迁移成功。失败需在主菜单明确提示，不静默忽略；旧键保留到迁移验证通过且有明确清理版本。
- 读档由 `GameRuntime` 先按存档的章节与地点加载对应阶段场景和章节模块，成功后提交恢复状态，再调用 `OnResume` 与 `OnLocationShown`；失败保留原检查点并显示原因，不进入错误阶段的同地点场景。

### 4.4 ChapterModule

```csharp
public abstract class ChapterModule : MonoBehaviour
{
    public abstract string ChapterId { get; }
    public virtual void OnEnter(GameRuntime rt) { }
    public virtual void OnResume(GameRuntime rt) { }
    public virtual void OnExit(GameRuntime rt) { }
    public virtual void OnLocationShown(GameRuntime rt, string locationId, string variant) { }
    public virtual bool HandleInteraction(GameRuntime rt, string locationId, string action) => false;
    public virtual bool HandleItemUse(GameRuntime rt, string itemId, string locationId, string action) => false;
    public virtual void OnTick(GameRuntime rt, float deltaTime) { }
    public virtual string GetObjective(GameRuntime rt) => "";
    public virtual string GetProgress(GameRuntime rt) => "";
}
```

- 只有 `StoryDirector.Active` 模块接收 `HandleInteraction` / `OnTick`。
- 模块通过 `rt.State` 读写状态，通过 `rt.Dialogue/Info/Memo` 显示内容，通过 `rt.GoTo(locationId, variant)` 切地点，通过 `rt.Checkpoint()` 存档。
- 新章进入调用 `OnEnter`，读档恢复调用 `OnResume`，随后地点加载完成调用 `OnLocationShown`；`OnResume` 不得重复播放开场、再次扣 SAN 或重复发放物品。
- 章节推进：模块调用 `rt.StartChapter(nextChapterId, stepId, locationId, variant)`；核心先确认目标章节资源和地点存在，再切换模块、状态与地点。失败不提交新 `chapterId`。`StoryDirector` 负责 `OnExit/OnEnter`。
- S1→S2 交接的最小契约：`NightPhoto`、步骤 `bridgeReached`、地点 `BridgeOdd4F`、变体 `night`、P1 完成、照片和工牌在背包。S2 接管后展示两项**明确选择**，首次选择才写 `routeChoice`。S1 当前的完成面板只用于旧流程，接入新流程时由正式章节跳转替代。

### 4.5 StoryDirector

```csharp
public sealed class StoryDirector : MonoBehaviour
{
    public ChapterModule Active { get; }
    public bool CanLoad(string chapterId);
    public bool Enter(string chapterId, bool resume);
    public bool Route(string locationId, string action);
    public bool RouteItem(string itemId, string locationId, string action);
    public void Tick(float deltaTime);

```

- 每次仅实例化当前章节的预制体；路径和 ID 约定固定，便于各章独立提交。
- 章节缺失、ID 不符或预制体不含 `ChapterModule` 时返回失败并显示错误；不回退到另一章，不写入存档。

### 4.6 GameRuntime

常驻服务聚合与仲裁者：

```csharp
public sealed class GameRuntime : MonoBehaviour
{
    public GameState State { get; }
    public DialogueService Dialogue { get; }
    public InfoService Info { get; }
    public StoryDirector Story { get; }
    public LocationView CurrentLocation { get; }
    public bool IsModalOpen { get; }

    public bool GoTo(string locationId, string variant = null, string arrivalLine = null);
    public bool StartChapter(string chapterId, string stepId, string locationId, string variant);
    public void Interact(string locationId, string action);
    public bool UseItemOn(string itemId, string locationId, string action);
    public bool Checkpoint();
    public void RestartFromSave();
    public void ReturnToTitle();
}
```

- `Interact`：先判断模态；再交给 `Story.Route`；未处理时记录警告（便于发现遗漏热点）。
- `GoTo`：用当前 `chapterId` 和目标 `locationId` 查场景注册表并验证 Build Settings → 叠加加载目标 Scene → 找到并校验唯一 `LocationView` 及其章节/地点归属 → 应用场景内照明/演出状态 → 更新 `State.locationId/variant` → 卸载旧地点 → 通知 `Story.Active.OnLocationShown` → 刷新 Overlay。操作期间锁定点击与存档；加载失败时保留旧地点与旧状态。
- `StartChapter`：先验证下一章的模块与 `(nextChapterId, locationId)` 场景组合，再执行切换；即使逻辑地点 ID 相同，也要加载下一阶段的场景，不能沿用上一阶段的场景对象。
- `UseItemOn`：先检查物品仍在背包，再将物品 ID、地点和热点动作交给当前章节；未处理时保留物品和选择状态，任务物不会被通用层消耗。
- `IsModalOpen`：聚合对白/信息/备忘/物品详情/暂停/过场，Overlay 与热点统一使用。

```csharp
public sealed class Hotspot : MonoBehaviour, IPointerClickHandler, IPointerEnterHandler, IPointerExitHandler,
    IBeginDragHandler, IDragHandler, IEndDragHandler
{
    public string action;
    public string label;

```

- 热点只转发动作，不持有进度；公共 action 在 `StoryIds`，章节专属 action 由各章独立定义并保持稳定。阶段专属热点留在对应场景；同一场景内的照明状态由 `LocationView` 与章节状态共同决定可见性和可点性。
- `BridgeOdd4F` 的夜间入口承接 S1 与 S2，`BridgeSpan4F` 承载中段玻璃留言，`BridgeEven4F` 承载资料柜；三处都能按剧情条件往返，不把跨栋空间塞进单张固定画面。
- 拖放能力由 `allowDrag/dropTarget` 开关，替代 `S1Hotspot` 里写死的 `action == "chair"`。

### 4.8 DialogueService / InfoService

- 共享 Yarn `DialogueService` 与自定义 uGUI 呈现器已建立；章节继续通过 `IDialogueContext` 接入。常驻核心迁移时复用该服务，不恢复旧 `Say` 队列。
- 立绘/排版规则由现有共享服务和配置维护；长文档由对话命令交给信息呈现层。
- 字体注入由 `GameRuntime` 启动时统一执行一次（常驻场景），地点场景不再各自建字体。

### 4.9 GameplayOverlay

- 仅持有 `GameRuntime` 引用；目标/时间/进度来自 `Story.Active` 与 `State`。
- `TryUseSelected` 改为向 `GameRuntime.UseItemOn(itemId, locationId, action)` 转发；物品栏按 `State.inventory` 构建，不硬编码仅照片/工牌。
- 不再有 `s0`/`s1` 字段与分支。

## 5. 运行流程

```text
Title
 └─ 开始/继续 -> Gameplay（常驻，单加载）
      ├─ 读档/新档 -> GameState
      ├─ StoryDirector 加载 ChapterPrologue（新档）
      ├─ 叠加加载 Exterior（新档）
      └─ 热点点击 -> GameRuntime.Interact
            └─ ChapterPrologue.HandleInteraction
                 ├─ 写 flags；在指定检查点调用 rt.Checkpoint()
                 ├─ rt.Dialogue.Say(...)
                 └─ rt.GoTo("Corridor5F", "day", 到达台词)
                        ├─ 叠加加载并验证 Corridor5F
                        └─ 卸载 Exterior
      └─ Prologue 完成 -> rt.StartChapter("NightPhoto", "photoDrop", "ClubRoom", "night")
            └─ ChapterNightPhoto 接管 P1/工牌/SAN
                 └─ 抵达 4F -> rt.StartChapter("BridgeRoute", "chooseRoute", "BridgeOdd4F", "night")
```

编辑器开发入口：在 WWG 编辑器中显式执行 `WWG/Dev/Play S2`，工具验证 `S2Bootstrap` 样本后打开 `Gameplay` 并注入其**内存副本**；该样本满足上面的 S1→S2 交接契约，不写 `WWG_Save`，不进入发布版 Build Settings。S2 可从此入口验证路线选择、P2 与返回 5F，即使 S1 尚未迁移完毕。

地点切换不再经过「复制整章控制器」或静态 `pendingTravel`，章节模块与状态常驻。

## 7. 章节模块示例

### 7.1 ChapterPrologue（原 S0）

- `OnEnter`：若新档，播放楼外开场；设置目标「前往单数栋 5F」。
- `HandleInteraction`：处理 `directory/enter/toRoom/toCorridor/toBridge/chair/sign/timer/guide/...`，读写 `flag.s0.*`。
- 全部记忆点满足后 `leader` 触发过场，调用 `rt.StartChapter("NightPhoto", "photoDrop", "ClubRoom", "night")`；`WWG_S0_Complete` 由 flag 取代。

### 7.2 ChapterNightPhoto（原 S1）

- `OnEnter`：初始化 SAN/生命（若新档），播放掉落照片对白。
- `HandleInteraction`：`box/curtain/lamp/chair/badge/glass/rest/toCorridor/toBridge`。
- P1 匹配用 `flag.p1.curtain|lamp|chair` 计数；完成时扣 SAN 一次并置 `flag.p1.shock`。
- `OnTick`：走廊危险计时、零 SAN 计时；死亡回安全屋但不丢物品/P1 进度（与现状一致，写入新状态模型）。
- 到达单数栋 4F 入口后交接给 `BridgeRoute`；入口开关只切换照明，首次调查连廊中段右侧玻璃时按当时的照明记录路线。该流程不依赖 S1 其余演出是否已精修。
- 与 Prologue 共用 `DialogueService`、`InfoService`、`GameplayOverlay`、存档。

### 7.3 后续章节

- `ChapterBridgeRoute`：首次调查右侧玻璃时按照明写一次 `RouteLight/RouteDark`；单/偶数栋海报与中段玻璃留言分别在对应地点场景。两路线均按 2741 取得借用便签，可返回 5F 休息；后续开关不改 `routeChoice`。
- `ChapterFinale`：`viewChoice = ViewTogether/ViewAlone`，两种结尾都从同一状态读取，不做低 SAN 随机。

## 9. 落地顺序与并行工作

### 9.1 当前重构顺序

1. **场景差分样板**：选同一地点的两个阶段场景，在 Unity 编辑器中核对层级、引用和画面后，只提取确实相同的静态结构到基础 Prefab；原场景保留各自的专属对象与位置 override。验证两场景的画面、热点和切屏，再逐地点扩展；已有场景不使用生成器重新创建。
2. **公共契约**：保留现有稳定章节/地点/物品 ID 和 `GameState`；建立 `(chapterId, locationId)` 显式场景映射、`ChapterModule` 回调、`GameRuntime` 加载事务与统一检查点规则。新增代码先独立编译，不改现有正式入口。
3. **常驻核心**：建立 `Gameplay.unity`、共享 Overlay、章节预制体加载器和阶段地点场景叠加加载。新流程使用独立开发入口；原 Title→S0/S1 流程继续可玩。
4. **逐章交接**：把 S0/S1 的状态、交互和 UI 接到常驻核心，再接通现有 S2–S4 场景与谜题。原 `WWG/Dev/Play S2/S3/S4` 保留为不写玩家存档的编辑器样本，直到正式流程验收。

每一步都保留可玩的入口；场景差分完成与正式流程接通分别验收，不将 Prefab 提取等同于 `GameRuntime` 已实现。

### 9.2 可同时进行的章节工作

| 工作包 | 主要文件所有权 | 输入 | 独立验收 |
| --- | --- | --- | --- |
| 核心与集成 | `Core/`、`Interaction/`、共享 `UI/`、`Gameplay.unity`、Build Settings | 本文公共契约 | 新/旧入口可分别 Play；存档往返 |
| S0/S1 迁移 | `ChapterPrologue`、`ChapterNightPhoto` 及对应独立预制体、原七个阶段场景与基础 Prefab | 公共契约、现有七场景 | Title→P1→工牌→4F 入口；各场景物件可独立调整，无重复冲击 |
| S2/P2 | `ChapterBridgeRoute` 及其预制体、4F 三地点、章节专属文本 | 公共契约、`S2Bootstrap` | 两条路线都得 2741 与借用便签，可往返 |

- 每位程序员使用自己的 Git 分支或 worktree；提交脚本、场景、预制体及对应 `.meta`，不提交 `Library/` 等生成物。Unity 版本与包锁定文件遵循现有项目基线。
- 不并行编辑同一个 `.unity`、基础 Prefab、共享预制体或 `ProjectSettings/EditorBuildSettings.asset`。新增场景由作者提供路径和 GUID，集成人统一登记 Build Settings；共享接口变更先改契约，再更新受影响章节。
- 不让旧场景被生成器或域重载自动覆盖。旧 S0/S1 完整迁移、正式 S1→S2 接通、新流程存读档验证后，才删除已退役的旧控制器和迁移工具；阶段场景继续作为正式资产使用。清理单独提交，便于回退。
- 每次合并检查编译、相关章节的编辑器 Play 路径、Unity YAML/meta 引用和存档版本。存档格式变更须提供版本迁移或明确兼容错误，不让加载器猜测章节。

### 9.3 集成与清理

1. 把 S0/S1 章节接入新流程，正式 Title 新档入口切到 `Gameplay`；S1 到达 4F 时交出交接状态，由 S2 接管，取消旧完成面板的阻塞。
2. 完成 P2→P3→结尾的正式连接，验证两条路线、两种查看选择、读档和 SAN/生命耗尽后的恢复。旧存档迁移在切换 Title 读档入口前完成并验证。
3. 最后仅删除被新流程取代的旧控制器、旧生成器与已过期文档条目；**不删除阶段场景**。同步更新 `AGENTS.md`、`架构规范.md`、`目录结构组织.md`、`运行流程.md`、`程序规范文档.md` 和场景工作流 skill。

## 10. 分阶段验收标准

### 阶段场景差分样板

- 两个同地点、不同阶段的场景继续分别打开、保存和调整场景专属物件；原场景 GUID 与 Build Settings 项不变。
- 两场景引用同一个基础 Prefab，公共结构一致；阶段专属热点、画面及位置 override 不会被修改基础 Prefab 时覆盖。
- 改动前后分别 Play 检查两个场景的点击、切屏、UI、对白和检查点；Unity Console 无新增错误。S2 两条路线仍能取得 2741 与借用便签，留暗后开灯不会改写路线选择。

### 全量迁移完成

- `Assets/Scenes` 保留 S0/S1 等阶段地点场景及其 GUID；旧阶段控制器退役后，Build Settings 含正式入口、常驻场景和已实现的阶段地点场景。
- 从 Title 可依次完成 S0→P1→4F 双栋 P2→3F P3→5F 安全屋→两种结尾；四种路线/结尾组合都可到达 Demo 终点。
- 暂停菜单的检查点读写保留章节、地点、变体、时间、flags、已触发对话、任务物、SAN/上限/生命和两次选择；错误或旧档迁移失败有明确提示。
- 生命耗尽后关键物品、P1/P2/P3 进度与选择不丢失。低 SAN 残影只给真实线索；5F 活动室仍为有电的安全屋。
- 同一地点的白天/夜间门窗与透视一致，各阶段场景的专属物件仍可单独调整；`GameplayOverlay` 与 `Hotspot` 不含 S0/S1 类型分支。相关 Play 路径与 Console 验证通过。
